# 日記庫檢查與修復

設定頁「日記庫」卡片提供檢查與修復流程。檢查可重建衍生索引，但不會移動或刪除正式日記/附件；修復前必須建立並驗證本機備份。

## 流程與摘要

1. **檢查前確認**：顯示「上次修復」紀錄（時間、備份、檢查篇數、剩餘問題）；尚未修復過則提示；確認按鈕是「開始檢查」。目前日記庫狀態仍由首頁卡片顯示，不在此重複。
2. **檢查日記庫**：掃描日記、日記旁的完成聊天、附件、搜尋資料與人物資料，重建衍生索引，寫入 `last_inspect_summary`。只記錄問題，不刪除、不搬移正式日記與附件。
3. **備份後修復**：先建立並驗證 `backup_before_repair_*.zip`，再執行實際 I/O；一般本機備份與修復前備份共用最新 5 份保留數。
4. `last_repair_summary` 是索引 SQLite 的 `app_kv` 單一覆寫值，不在備份內。因此還原或重建索引後會遺失，這是刻意設計；還原後以最新檢查結果代表目前狀態。
5. 動作紀錄與計數只來自實際成功的 I/O 事件，不由預計動作推算。`quarantinedCount` 只計仍在 quarantine 的檔案；已清除的壞附件不增加隔離數。

## 顯示規則

- 首頁日記庫卡片使用最新維護快照；時間格式不顯示星期。
- 詳細資料分為「已完成」、「全域清理」、「仍需處理」三區；只有三區都為空時才隱藏按鈕。
- 沒有 `entry_action_logs` 的舊摘要會顯示彙總 fallback 與未解決 findings，不虛構逐篇標題。
- 開始檢查前顯示這次會檢查的範圍。檢查有異常時，只在按下修復前補上修復會做的事。修復結果不再重複這段說明，並保留每一項的手動修復與永久刪除。檢查結果最多預覽 3 項，其餘寫未列出的數量；按下備份後修復仍處理全部。

## 附件與隔離

- 圖片會優先尋找同一附件 ID 的可驗證副本；失效引用、已確認孤立檔與壞附件在安全清理成功後直接移除，不列入手動修復。壞附件刪除只驗證路徑仍在 vault 內，不再用「正常附件」內容驗證卡住清理；清完後該篇不應再出現在「仍需處理」。
- 救援失敗或仍需保留的 entry-level 問題檔才移至 `vault/quarantine/<repair-id>/`。舊修復目錄只有在沒有未解決 entry-level 問題時才會清除；清除失敗會記為 `cleanupFailure`。
- 只有實際隔離成功才計入 `quarantinedCount`。沒有隔離內容時不建立空的當次 repair metadata 目錄；完整備份排除 `quarantine/`（見[備份與還原](./備份與還原.md)）。

日記改日期、修復搬移與隔離也一起處理相鄰聊天。清理重複日記前先保留聊天於權威位置；聊天內容衝突或無法確認解密內容一致時，保留來源並回報清理失敗，不覆寫或靜默刪除。

完成聊天 `*.chat.json.enc` 會在檢查時解密，並用聊天內容核對日記庫與 `generated_entry_id`。`.previous`、`.tmp` 只當同伴，不單獨成一項。讀不了、日記庫不符或對不上這篇日記時，記在該篇上，日記本體不動。沒有對應 `.md.enc` 的檔與無法確認所屬日記的附件一樣，記成孤立項目。修復只把這些聊天檔和同伴隔離到 `quarantine/<repair-id>/`。可讀且對得上的聊天留在原位。AI 設定與未完成聊天草稿不掃描、不刪除。

日記離開 `entries/` 時刪掉 `diary_organization_drafts/{entryId}/`，包含永久刪除、隔離與清掉重複日記。搬回正確日期不刪，因為草稿依日記 ID 存放。不是日記 ID 的目錄不碰。

聊天的 `.previous` 與 `.tmp` 都是恢復資料，複製時保留既有檔案，不能把 `.tmp` 當作工作暫存覆寫。複製失敗保留來源，並清除這次未完成的目的檔。

## 手動修復與永久刪除

- 手動修復會從 finding 嘗試取出可讀內容，寫入一次性 `__salvage_<新 ID>` 草稿並開啟編輯器；只有日記本體確實可搶救時才顯示按鈕。
- 新日記、附件與索引成功提交後，才刪除舊問題檔；取消或儲存失敗時保留舊檔。
- 永久刪除處理該 finding 對應的 `entries/`／`assets/` 檔案；刪除日記時同步移除相鄰聊天 JSON、`.previous`、`.tmp` 與該篇整理草稿。只刪完成聊天時，日記與整理草稿留著，並一併刪掉該聊天的同伴檔。
- 手動修復或永久刪除後，會更新同一份最新修復摘要：保留歷史動作，重新計算 issue counts/findings，`finishedAt` 不變，更新 `lastUpdatedAt`、`salvagedCount` 或 `permanentlyDeletedCount`；相關 providers 會失效，設定頁因此刷新。
