# 解鎖與會話

有效內容存取需要 `status == unlocked && session != null`。完整還原可在受控流程搬移密文，不代表已取得內容存取權。本文的 resume 指 App 回到前景；Drive 上傳沒有遠端驗證完成前的跨程序續傳。

主要協調由 [`AppSessionController`](../../../lib/application/session/app_session_controller.dart)、[`SessionStartupCoordinator`](../../../lib/application/session/session_startup_coordinator.dart) 與 [`SessionResumeCoordinator`](../../../lib/application/session/session_resume_coordinator.dart) 負責；金鑰與檔案格式見[加密格式](加密格式.md)。

## 解鎖模式

| 模式 | 儲存值 | 驗證與裝置包裝 | Keystore auth kind |
|------|------|------|------|
| 無 | `none` | 不跳系統驗證，仍透過可信裝置解開包裝金鑰 | `plain` |
| 裝置螢幕鎖 | `deviceLock` | 系統螢幕鎖驗證 | `deviceCredential` |
| 生物驗證 | `biometric` | 系統生物驗證，可有螢幕鎖後備 | `biometric` |

`deviceLock` 與 `biometric` 都要求裝置螢幕鎖。建立或切換至生物驗證包裝時，`migrate` 檢查還要求已登錄強生物辨識；日常 `unlock` 檢查只要求螢幕鎖可用，因此移除生物辨識後仍可能透過後備驗證解鎖。規則見 [`unlock_mode_policy.dart`](../../../lib/infrastructure/security/unlock_mode_policy.dart)。

模式偏好在日記庫外的 `app_lock_store.json`；索引的 `keystore_wrap_mode` 只是同步標記。只有標記落後、裝置 slot 與包裝記錄已符合策略時，僅更新標記，不重新包裝。

## Session 狀態與 Provider

[`AppSessionState`](../../../lib/application/session/session_state.dart) 保存 `status`、`session`、`message`、`failure`、`lockReason`；`failure` 目前用於標示 `unreadableIndex`。不能只用 `isUnlocked` 判斷已有可讀日記庫。

| 狀態 | 意義 |
|------|------|
| `uninitialized` | 尚未完成 bootstrap |
| `unlocking` | 正在驗證或準備可信裝置 session |
| `unlocked`，有 session | 可由有效 session 讀寫日記庫、草稿與索引 |
| `unlocked`，無 session | 通常為尚未建立 Recovery Key；顯示[首次啟動](../功能/首次啟動.md)畫面 |
| `locked` | 需重新驗證，不提供有效內容 session |
| `recoveryRequired` | 可信裝置路徑不可用，需 Recovery Key |
| `fatalError` | 啟動或驗證流程遇到無法繼續的一般錯誤 |

[Provider](../../../lib/application/session/session_providers.dart) 各有不同用途：

| Provider | 責任 |
|------|------|
| `appSessionProvider` | 執行期主狀態與操作入口 |
| `sessionStartupProvider` | 啟動初始化；由 effective provider 在 `uninitialized` 時接入 |
| `effectiveAppSessionProvider` | 合併啟動與執行期狀態，供 UI 使用 |
| `activeVaultSessionProvider` | 僅在 unlocked 時輸出 session；首次啟動仍可能為 null |
| `indexQueryableVaultSessionProvider` | 解鎖期間暫留上一個已知 session，避免查詢視圖閃斷；其他無效狀態清空 |

查詢 Provider 暫留 session 是顯示穩定性措施，不是一般寫入或轉移操作的授權入口。

## 冷啟動 bootstrap

`bootstrapSession()` 依序：

1. 檢查日記庫 runtime 支援；目前僅 Android，其他平台進 `fatalError`。
2. `VaultRepository.initialize()` 準備目錄與 metadata。
3. 無 `recovery.json` 時進 `unlocked + session:null`，引導建立或還原日記庫。
4. 有 recovery metadata、無可信裝置記錄時進 `recoveryRequired`。
5. 有可信裝置時呼叫 `unlock()`；成功才啟用 session。

取消或暫時驗證失敗通常留在 locked；包裝記錄損壞、Keystore 失效、金鑰認證錯誤或索引仍不可讀等會清除裝置信任並導向 Recovery Key。一般未知錯誤才進 `fatalError`；實際分類見下方失敗處理。

## Startup Phase 與 lifecycle 隔離

啟動週期另以 `SessionStartupPhase` 隔離冷啟動事件與真正的背景返回：

| 階段 | 行為 |
|------|------|
| `bootstrapping` | 不參與 lifecycle 自動解鎖 |
| `awaitingFirstBackground` | bootstrap 已結束，等待啟用 resume 判定 |
| `resumeUnlockArmed` | lifecycle bridge 可記錄背景事件並安排自動解鎖 |

bootstrap 結束後，已有有效 session 時會在約 500ms 後啟用 resume 判定。只有啟用後、當下允許處理 lifecycle resume 的 `paused`／`hidden`，才標記為自動解鎖所需的「曾進背景」。因此第一個冷啟動 `resumed` 不會直接再要求驗證。

這個背景標記與 watchdog 的逾時計時用途不同；不能把 startup phase 當作停止所有背景計時的開關。

## 可信裝置解鎖

可信裝置需要 Android Keystore slot 與 secure storage 的 `WrappedRecoveryKeyRecord` 同時有效。它先恢復日記庫的 `recoveryWrapKey`，不逐檔透過 Keystore 解 LDJ2。

`openTrustedSessionEnsuringKeystore()` 的主要分流：

1. 讀 recovery metadata、包裝記錄與目前模式要求的 auth kind。
2. slot 符合策略時走 `openTrustedSession()`，再同步 Keystore 狀態；僅索引後綴落後時只補寫後綴。
3. slot 不符合時，以原生驗證完成 unwrap／rewrap，保存新包裝記錄並清除非使用中的裝置金鑰。
4. 處理已中斷的金鑰維護、驗證日記庫樣本並準備索引。
5. 回傳包含日記庫 ID、包裝金鑰、裝置信任旗標與 slot ID 的 `UnlockedVaultSession`。

`ensureIndexReady()` 在結構不相容或日記檔與索引路徑不一致時重建；重建後仍列不進索引的檔若沒有變動，不會讓每次解鎖都重掃。細節見[索引資料庫](../資料/索引資料庫.md)。

## Recovery Key 解鎖

`AppSessionController.unlockWithRecovery()` 經復原服務進入 `VaultRepository.unlockWithRecoveryKey()`：

1. 依 recovery metadata 衍生包裝金鑰，處理既有輪替 pending，驗證樣本後再完成 pending 清理。
2. 檢查目前解鎖模式的建立包裝能力；輸入正確金鑰也不會略過裝置能力檢查。
3. 檢查分身替換狀態，再依下表分流。

| 分流 | 金鑰與裝置信任 | 索引及分身 |
|------|------|------|
| 正常 | 建立裝置金鑰、逐檔 rewrap、保存包裝記錄與保護後綴 | 重建索引後清除進行中旗標 |
| 分身主檔缺失而只剩替換副本 | 建立 `trustedDevice:false`、包裝金鑰只留記憶體的復原 session；不新增裝置信任 | 先開啟索引，不走正常整庫 rewrap／強制重建，也不自動啟用舊分身 |

`AppSessionController` 會確認索引可用，再啟用該復原會話。一般流程由日記庫層完成裝置包裝，分身異常時則使用未建立裝置信任的復原會話。

金鑰或驗證失敗時進 `recoveryRequired` 並保留錯誤訊息。上述復原 session 仍可讀寫能正常解密的資料，不是唯讀模式；差別在於不新增裝置信任、不自動啟用舊分身。關閉後仍須重新取得可用金鑰。替換副本及 pending 規則見[本機儲存](../資料/本機儲存.md#遠端清理-json-與金鑰維護)。

## 更新復原金鑰

設定頁先產生僅保留在記憶體中的新金鑰。保存對話框提供敏感剪貼簿複製，使用者勾選已安全保存並確認後，才開始修改日記庫。取消對話框、裝置鎖定或會話更換會放棄這次確認。

輪替比對原金鑰世代後，先按解鎖方式取得 Keystore 授權。取消時保留原金鑰。授權後保存加密續跑紀錄、更新加密檔與索引，最後保存新裝置包裝並標記待備份。中斷由[金鑰維護](../資料/本機儲存.md#遠端清理-json-與金鑰維護)處理。既有備份沿用建立時的復原金鑰。

## 背景逾時

[`SessionInactivityWatchdog`](../../../lib/application/session/session_inactivity_watchdog.dart) 預設 3 分鐘，可選 1／3／5／10 分鐘：

- `paused`／`hidden` 開始記錄背景時間；`inactive` 不啟動此計時。
- 背景 timer 到期即觸發鎖定；系統暫停執行時，回到 `resumed` 也會先檢查經過時間。
- 回前景若已逾時，立即處理逾時；尚未逾時才等待約 500ms 穩定期，再清除背景紀錄。
- 解鎖狀態下的 pointer down 也會清除背景追蹤。前景沒有一般閒置倒數。

逾時使狀態成為 `locked + lockReason:inactivity`，保存鎖定前路由，停止提供有效 session 並清理已開資源。解鎖後可返回原編輯器或聊天室。

### 長作業與畫面遮蔽

`runSensitiveTask()` 與 `runBackgroundSafeTask()` 執行期間暫停 watchdog，結束且 session 仍有效時重新啟用；若任務結束時仍在背景，從該時點重新計時。這不會禁止手動鎖定，且鎖定時仍有受保護任務，實體資源清理會延後到任務結束。

| 作業 | 邊界 |
|------|------|
| AI 日記生成 | sensitive task 包住材料準備、單次請求與草稿提交；背景仍遮蔽畫面，手動鎖定或 session 失效會取消，晚到結果不得寫回 |
| 聊天回覆 | 沿用背景逾時鎖定規則 |
| Drive 備份 | ZIP 準備使用 background-safe task；交給原生前景服務後 session 可正常鎖定，上傳與成功收尾不依賴解鎖 |

Drive 自動收尾只使用非互動授權。Android 視窗在失焦或暫停時維持原畫面。App 允許系統截圖，「最近使用的 App」卡片採用 Android 預設預覽，可能顯示離開前的日記內容。

## 回前景（resume）自動解鎖

[`AppLifecycleSessionBridge`](../../../lib/app/app_lifecycle_session_bridge.dart) 收到 `resumed` 時，先讓 watchdog 判定逾時，再檢查：

1. 已進 `resumeUnlockArmed`，且沒有正在進行的解鎖。
2. 本啟動週期確實記錄過有效背景事件。
3. `status == locked && lockReason != manual`。

符合時約等 350ms，再核對前景與狀態是否仍有效，呼叫 `unlock(source:lifecycleResume)`；切回背景或啟動週期改變會取消待執行請求。實際系統驗證方式依上方模式表。

### 驗證取消與失敗

| 結果 | 狀態 |
|------|------|
| 使用者取消或驗證逾時 | 原有 lock reason 存在時保留原因與訊息；沒有時轉 `authFailed` |
| 認證失敗、驗證鎖定、未登錄生物辨識或原生回報無裝置憑證 | 通常為 `locked + authFailed`，顯示重試或能力訊息 |
| 模式能力檢查不通過、包裝格式不支援、Keystore invalidated、可信 session 不可用或 StateError | 清除裝置信任，進 `recoveryRequired` |
| 金鑰認證錯誤或加密索引仍不可讀 | 清除裝置信任，進 `recoveryRequired`；索引錯誤另帶 failure |
| 其他未知錯誤 | `fatalError` |

同樣是「無裝置憑證」，由能力預檢或原生驗證回報會走不同分類；應依實際例外型別處理，不只比對訊息文字。索引開啟層已嘗試自動刪檔重開一次，仍失敗才往上層分類。

## 手動上鎖與手動重驗證

手動上鎖進 `locked + lockReason:manual` 並停止 watchdog，不因 resume 自動再打開。使用者按「重新驗證」才再次走 `unlock()`。設定頁取消進行中的驗證並改為手動重驗證，也會將鎖定原因設為 manual。

## 還原後的 session 分流

還原使用 [`finishRestoreSession()`](../../../lib/application/restore/post_restore_session.dart)，先 `beginPostRestoreStartup()`、關閉舊資源並 invalidate 日記庫、索引與設定相關 Provider，避免一般啟動與還原啟動互相競爭。

| 條件，依順序判斷 | 行為 |
|------|------|
| 已提供非空備份 Recovery Key | `unlockWithRecovery()`；索引是否重建依上方復原分流 |
| precheck 允許沿用 live prior session | `resumeSessionAfterRestore()` 重用包裝金鑰，驗證樣本，準備並重建索引，不要求裝置驗證 |
| 預期 trusted unlock，但 live session 已不符 | 進 `recoveryRequired` |
| 其餘 | `bootstrapAfterRestore()`；若成功取得 session 且未走前兩條，由還原收尾補重建索引 |

沿用 session 要求同日記庫、同 KDF salt、裝置具可信存取資料，且換入前仍有可用包裝金鑰；不單憑檔名或 `trustedDevice` 布林判定。詳見[還原預檢](../功能/備份與還原.md#還原)。

收尾在 finally 清除路由快照與啟動旗標；成功後刷新首頁與人物資料。日記庫已換入但解鎖失敗時，應保留備份與原金鑰並處理復原，不把啟動失敗誤報為未曾替換資料。

## 切換解鎖模式

[`UnlockModeChangeService.apply()`](../../../lib/infrastructure/security/unlock_mode_change_service.dart) 要求有效 session。目標模式相同時直接成功；不同時依序：

1. 做 `migrate` 能力預檢。
2. `ensureKeystoreMatchesUnlockMode(session, targetMode:mode)` 調整裝置保護。
3. 成功才寫入模式偏好，並接回可能帶新 slot ID 的 session。

取消系統驗證或同步失敗，不先改寫偏好。此操作改變裝置層保護，不輪替 Recovery Key，也不必逐檔重加密日記庫。可信裝置只是便利入口；記錄或 Keystore 失效、還原世代不符時，仍須使用 Recovery Key。
