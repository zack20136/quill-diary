# 索引資料庫

`index/journal_index.sqlite` 是加密的衍生索引，正式日記與人物名冊的權威資料位於 `vault/`。首頁搜尋、日曆、摘要與人物分析使用索引，不會在每次查詢時逐篇解密日記。草稿及聊天不加入一般日記索引。

## 路徑與加密

路徑由 `VaultPathStrategy.indexDatabasePath()` 提供，位於 `{applicationSupport}/quill_diary/index/`，與日記庫分開，也不納入完整備份。使用 SQLite3 Multiple Ciphers（sqlite3mc），由 [`openIndexConnection()`](../../../lib/infrastructure/database/index_database_connection_io.dart) 設定加密金鑰並讀取 `sqlite_master` 確認可開啟；沒有明文 SQLite fallback。Cipher 可用性在 Release 也必須通過；Cipher 不可用與索引損壞分開處理，前者不得進入刪除重建分支，兩者都不得刪除正式日記與附件。

金鑰由 session 的 `recoveryWrapKey` 與 `vaultId` 經 HKDF-SHA256 衍生，參數見[加密格式](../安全/加密格式.md#搜尋索引金鑰衍生)。索引包含正文搜尋文字及人物命中資料，雖可重建，仍是需保護的內容資料。

## 資料表與欄位

Schema 與查詢定義在 [`index_database.dart`](../../../lib/infrastructure/database/index_database.dart)，目前 `schemaVersion` 為 `DataVersions.indexDatabase == 1`。人物比對規則的快取修訂由 [`PersonNameMatcher.rulesRevision`](../../../lib/domain/people/person_name_matcher.dart) 管理：規則改變時遞增，讓舊分析重新計算，不屬於資料格式版本；一般分析、讀寫或重建索引不調整這兩種版本。

| 表 | 用途 |
|------|------|
| `entries_index` | 日記識別、日期、搜尋文字、預覽、統計及檔案狀態 |
| `entry_tags` | 日記標籤與正規化文字 |
| `entry_attachments` | 附件摘要、類型、計數及預覽路徑 |
| `people_analysis_documents` | 已分析日記的內容 hash，包含零命中的日記 |
| `entry_people_analytics` | 人物姓名命中結果；由人物功能按需更新 |
| `app_kv` | 重建／rewrap／維護摘要及人物分析狀態 |
| `tag_styles` | 標籤色彩快取，權威來源是 `vault/tag_styles.json.enc` |

`entries_index` 的主要欄位：

| 類別 | 欄位 |
|------|------|
| 識別與檔案 | `id`、`vault_id`、`file_path` |
| 標題與預覽 | `title`、`preview_text`、`preview_markdown` |
| 搜尋與可見文字 | `title_search_text`、`body_search_text`、`body_visible_text` |
| 時間 | `date`、`created_at`、`updated_at` |
| 統計 | `word_count`、`char_count`、`attachment_count`、`has_attachments` |
| 同步輔助 | `encrypted_file_size`、`encrypted_file_mtime`、`content_hash` |

domain 的 `DiaryEntrySummary` 合併標籤、附件數量及預覽圖等資料，讓列表不必另外讀取正式日記。

### `app_kv` 狀態

| Key | 用途 |
|------|------|
| `last_rebuild_at` | 最近全量重建時間 |
| `unindexed_entry_files` | 重建後仍無法列入索引的日記檔簽名；檔案沒變時解鎖不再重掃 |
| `rewrap_in_progress`、`rewrap_started_at` | 日記庫重新包裝／金鑰維護的進行中旗標與開始時間，不是逐檔完成清單 |
| `keystore_wrap_mode` | trusted device 保護所用 auth kind 後綴 |
| `people_analytics_generation` | 姓名比對規則版本 |
| `people_analytics_catalog_fingerprint` | 最近使用的人物姓名／別名集合指紋 |
| `people_analytics_stale` | 是否仍需補完分析；中斷後以內容 hash 接續 |
| `last_inspect_summary`、`last_repair_summary` | 最近檢查／修復摘要，不是正式日記資料 |

`app_kv` 不保存跨還原必須保留的使用者偏好；人物名冊與標籤樣式的權威來源仍在日記庫。不過，進行中的維護旗標也在這裡，不能把整個資料庫當成隨時可刪的無狀態快取。刪檔會同時失去維護摘要與旗標；輪替另有加密 pending，兩者用途見[金鑰維護](本機儲存.md#遠端清理-json-與金鑰維護)。

## 搜尋與人物分析

`searchEntries()` 先以 `normalizeSearchText(query)` 正規化輸入，空白查詢回傳全部列表；否則跳脫 LIKE 萬用字元後，以 `%查詢字%` 比對標題、正文搜尋文字與 `entry_tags.tag_normalized`；`preview_text` 不參與搜尋。

Markdown 抽取器一次產生搜尋正文、可見正文與預覽。`body_visible_text` 排除 fenced code、inline code、圖片網址及連結目的地，用於人物姓名分析。分析分批補建與失效規則見[人物與姓名查詢](../功能/人物與姓名查詢.md)。

## 開啟與 schema

[`IndexDatabaseManager.openForSession()`](../../../lib/infrastructure/database/index_database_manager.dart) 序列化開啟、關閉、換鑰及刪除。日記庫 ID 與衍生索引金鑰皆相同時才重用連線。

復原金鑰輪替時用 SQLite3 Multiple Ciphers 就地更新索引金鑰，保留既有索引內容與維護旗標。若輪替中斷，回復時可使用續跑紀錄中的另一代金鑰開啟索引，再改回舊金鑰。索引主檔不存在時先清除其孤立的 `-wal`、`-shm`、`-journal`，再建立新索引。

需要新連線時，先要求 session 有包裝金鑰，再衍生索引金鑰並初始化。只有 [`isUnreadableEncryptedIndexError()`](../../../lib/infrastructure/database/index_database_errors.dart) 辨識的錯誤才會自動刪檔重開一次，包括 SQLite `NOTADB`，或設定金鑰時出現讀取不足且索引主檔大於 0、未滿 512 位元組的情況。一般 I/O 或其他 SQL 錯誤直接向上回報。刪除涵蓋主檔、`-wal`、`-shm`、`-journal`，並先關閉連線。

`VaultRepository.ensureIndexReady()` 接著檢查結構：

1. `initialize()` 就地補建可安全新增的 `preview_markdown`、`body_visible_text` 與人物分析表，保留既有資料。
2. `hasExpectedIndexSchema()` 檢查 `entries_index` 必要欄位，並拒絕仍含 `mood`、`schema_version` 的結構；它不是所有資料表、約束與資料內容的完整驗證器。
3. 其餘不相容結構刪除重開，再由正式日記庫重建。
4. 相容時比對索引路徑與 `entries/**/*.md.enc`。磁碟有檔沒列入，或索引指到已不存在的檔，就從正式日記庫重建；否則只確保人物表存在並同步標籤樣式。
5. 重建後仍列不進索引的檔，把路徑、大小與修改時間的簽名寫入 `unindexed_entry_files`。簽名不變時下次解鎖不再重掃。還原流程緊接著會全量重建，因此該次略過對帳。

新建空索引同樣可能具有相容 schema，「開啟／刪檔重開」本身不會重建內容，要由解鎖時的對帳補上。缺少 `last_rebuild_at` 本身仍不會觸發全掃。

補欄後既有列的 `body_visible_text` 為 SQL NULL，人物相關功能再分批補建；不要把 NULL 與已分析但正文為空字串混為一談。

## 生命週期與同步

| 時機 | 行為 |
|------|------|
| 一般 trusted unlock | 開啟連線、檢查 schema；日記檔與索引對不上時重建，否則同步標籤樣式 |
| Recovery Key 解鎖 | 正常 rewrap 後重建；分身替換異常的復原 session 先開啟索引，再由 `ensureIndexReady()` 檢查，必要時重建 |
| 還原後沿用 session | `ensureIndexReady()` 後重建 |
| 日記正式儲存／刪除 | 同步主索引、標籤與附件；草稿輸入不更新 |
| 正常 Recovery Key 全庫 rewrap、金鑰輪替及檢查／修復流程 | 依各維護入口從正式日記庫對齊；單純裝置層包裝或後綴同步不等同全庫重建 |
| 明確重建 | 從正式日記與附件重新產生索引 |
| 鎖定、逾時或 reset | 關閉資源；一般鎖定不刪除索引檔 |

首頁查詢使用 `indexQueryableVaultSessionProvider`，在 `unlocking` 期間暫留上一個已知 session；鎖定或 session 不可用時回傳空結果。

`VaultRepository.rebuildIndex()` 實際委派日記庫檢查流程，掃描日記、完成聊天與附件，再清除並重建日記、標籤、附件及人物分析衍生列，更新 generation／時間並同步標籤。它接著會等待 `ensurePeopleAnalyticsReady()` 補齊人物分析；一般解鎖與查詢的按需補建是另一條路徑。

其中底層 `IndexDatabase.rebuild()` 只清除衍生列，不刪掉整個資料庫，也不清空所有 `app_kv`；不能單獨呼叫它就當成已完成正式資料重建。

釘選只在能確認正式日記清單完整時修剪，避免損壞日記導致釘選資料被誤刪。還原與維護流程見[備份與還原](../功能/備份與還原.md)、[日記庫檢查與修復](../功能/日記庫檢查與修復.md)。

## 開發與排錯

| 現象 | 先檢查 |
|------|------|
| 正式日記存在但列表少篇 | 解鎖比對日記檔與索引路徑，不一致就重建；重建後仍進不了列表的檔以 `unindexed_entry_files` 記住，檔案有變才再掃 |
| 正式日記存在但搜尋不到 | session 是否可查詢、儲存後索引／Provider 是否刷新、正規化搜尋文字是否更新 |
| 草稿文字搜尋不到 | 屬預期；先正式儲存，不把草稿補進日記索引 |
| 人物命中尚未完整 | 分析 stale／catalog fingerprint、內容 hash 與批次補建進度，不直接改人物名冊 |
| 換金鑰或還原後無法讀取 | 舊索引連線與金鑰是否已關閉／重建，不以明文 SQLite 作為 fallback |
| schema 升級後資料遺失 | 是否誤把可就地補欄的舊結構當成不相容；以真實前版資料庫測試初始化 |

全量重建會清空並重建日記、標籤、附件與人物分析衍生列，不應在一般查詢或每次 trusted unlock 反覆執行。修改索引 schema 時，一併檢查 `initialize()`、`hasExpectedIndexSchema()`、寫入與讀取映射，測試須涵蓋「前版結構＋既有資料 → 新版開啟」，不能只測目前 schema 自己初始化。
