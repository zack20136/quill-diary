# 索引資料庫

`index/journal_index.sqlite` 是加密的衍生索引，權威資料位於 `vault/`。首頁搜尋、日曆、摘要與人物分析使用索引，不會在每次查詢時逐篇解密日記。草稿及聊天不加入一般日記索引。

## 路徑與加密

路徑由 `VaultPathStrategy.indexDatabasePath()` 提供，與 vault 分開。金鑰由 session 的 `recoveryWrapKey` 與 `vaultId` 經 HKDF-SHA256 衍生，參數見[加密格式](../安全/加密格式.md#搜尋索引金鑰衍生)。

## 資料表與欄位

Schema 與查詢定義在 [`index_database.dart`](../../../lib/infrastructure/database/index_database.dart)。

| 表 | 用途 |
|------|------|
| `entries_index` | 日記識別、日期、搜尋文字、預覽、統計及檔案狀態 |
| `entry_tags` | 日記標籤與正規化文字 |
| `entry_attachments` | 附件摘要、類型、計數及預覽路徑 |
| `people_analysis_documents` | 已分析日記的內容 hash，包含零命中的日記 |
| `entry_people_analytics` | 人物姓名命中結果；由人物功能按需更新 |
| `app_kv` | 索引 generation、重建／rewrap／維護摘要及人物分析狀態 |
| `tag_styles` | 標籤色彩快取，權威來源是 `vault/tag_styles.json` |

`entries_index` 的主要欄位：

| 類別 | 欄位 |
|------|------|
| 識別與檔案 | `id`、`vault_id`、`file_path` |
| 標題與預覽 | `title`、`preview_text`、`preview_markdown` |
| 搜尋與可見文字 | `title_search_text`、`body_search_text`、`body_visible_text` |
| 時間 | `date`、`created_at`、`updated_at` |
| 統計 | `word_count`、`char_count`、`attachment_count`、`has_attachments` |
| 同步輔助 | `encrypted_file_size`、`encrypted_file_mtime`、`content_hash` |

`EntryIndexRecord` 合併標籤、附件數量及預覽圖等資料，讓列表不必另外讀取正式日記。

### `app_kv` 狀態

| Key | 用途 |
|------|------|
| `last_rebuild_at`、`index_generation` | 全量重建時間與目前索引 generation |
| `rewrap_in_progress`、`rewrap_started_at` | trusted device rewrap 的進度與開始時間 |
| `keystore_wrap_mode` | trusted device 保護所用 auth kind 後綴 |
| `people_analytics_generation` | 姓名比對規則版本 |
| `people_analytics_catalog_fingerprint` | 最近使用的人物姓名／別名集合指紋 |
| `people_analytics_stale` | 是否仍需補完分析；中斷後以文件 hash 接續 |
| `last_inspect_summary`、`last_repair_summary` | 最近檢查／修復摘要，不是正式日記資料 |

這些值只描述索引與同步狀態。刪除索引後維護摘要也會遺失；不能把 `app_kv` 當作跨還原必須保存的使用者設定。人物名冊與標籤樣式的權威來源仍在 vault。

## 搜尋與人物分析

`searchEntries()` 先以 `normalizeSearchText(query)` 正規化輸入，再以 `%query%` 做 SQL `LIKE`，命中標題、正文搜尋文字與 `entry_tags.tag_normalized`；`preview_text` 不參與搜尋。

Markdown 抽取器一次產生搜尋正文、可見正文與預覽。`body_visible_text` 排除 fenced code、inline code、圖片網址及連結目的地，用於人物姓名分析。分析分批補建與失效規則見[人物與姓名查詢](../功能/人物與姓名查詢.md)。

## 開啟與 schema

[`IndexDatabaseManager.openForSession()`](../../../lib/infrastructure/database/index_database_manager.dart) 綁定 session、衍生金鑰並初始化資料庫，不重掃 vault。已開啟且 vault ID 相符時重用連線；遇到不可讀的加密索引會刪檔重開一次。

`VaultRepository.ensureIndexReady()` 接著檢查結構：

1. `initialize()` 就地補建可安全新增的 `preview_markdown`、`body_visible_text` 與人物分析表，保留既有資料。
2. `hasExpectedIndexSchema()` 確認必要欄位，並拒絕仍含 `mood`、`schema_version` 等已移除欄位的結構。
3. 其餘不相容結構刪除重開，再由正式 vault 重建。
4. 相容時只確保人物表存在並同步標籤樣式，不因缺少 `last_rebuild_at` 而全量重掃。

舊列的 `body_visible_text` 留空，首次進入人物相關功能才分批補建。

## 生命週期與同步

| 時機 | 行為 |
|------|------|
| 一般 trusted unlock | 開啟連線、檢查 schema、同步標籤樣式 |
| Recovery Key 解鎖 | 底層重建索引，application 層再確認可用性 |
| 還原後沿用 session | `ensureIndexReady()` 後重建 |
| 日記正式儲存／刪除 | 同步主索引、標籤與附件；草稿輸入不更新 |
| 金鑰輪替、rewrap、檢查／修復或明確重建 | 從正式 vault 重新對齊 |
| 鎖定、逾時或 reset | 關閉資源；一般鎖定不刪除索引檔 |

首頁查詢使用 `indexQueryableVaultSessionProvider`，在 `unlocking` 期間暫留上一個已知 session；鎖定或 session 不可用時回傳空結果。

`rebuildIndex()` 掃描日記與附件、重建搜尋資料、更新 generation／時間並同步標籤。釘選只在能確認正式日記清單完整時修剪，避免損壞日記導致釘選資料被誤刪。還原與維護流程見[備份與還原](../功能/備份與還原.md)、[日記庫檢查與修復](../功能/日記庫檢查與修復.md)。

## 開發與排錯

| 現象 | 先檢查 |
|------|------|
| 正式日記存在但搜尋不到 | session 是否可查詢、儲存後索引／Provider 是否刷新、正規化搜尋文字是否更新 |
| 草稿文字搜尋不到 | 屬預期；先正式儲存，不把草稿補進日記索引 |
| 人物命中尚未完整 | 分析 stale／catalog fingerprint、文件 hash 與批次補建進度，不直接改人物名冊 |
| 換金鑰或還原後無法讀取 | 舊索引連線與金鑰是否已關閉／重建，不以明文 SQLite 作為 fallback |
| schema 升級後資料遺失 | 是否誤把可就地補欄的舊結構當成不相容；以真實前版資料庫測試初始化 |

全量重建會清空並重建日記、標籤與附件索引，不應在一般查詢或每次 trusted unlock 反覆執行。修改索引 schema 時，一併檢查 `initialize()`、`hasExpectedIndexSchema()`、寫入與讀取映射，測試須涵蓋「前版結構＋既有資料 → 新版開啟」，不能只測目前 schema 自己初始化。
